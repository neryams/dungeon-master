# Verification

Automated coverage includes atomic batches, duplicate-operation recovery, stale revisions, concurrent writers, replay after cache removal, interrupted temporary files, resource and inventory invariants, dice retries, corrections, map movement, public/private filtering, backup restore, invalid paths and archive entries, journal outage and lost acknowledgements, real MCP tool enumeration and a fresh stdio process resume.

The real journal integration uses the pinned upstream server and an isolated daemon. It intentionally uses an invalid embedding model identifier to test the upstream keyword-search fallback without downloading a model. This verifies journal persistence and retrieval, not vector quality or performance.

The acceptance scenario uses the original Lantern at Briar Ford adventure. It creates party/world state, records narrative details, resolves a potion and encounter, saves a checkpoint, restarts the service, and verifies exact continuation. This is a scripted playthrough, not an independent evaluation of model storytelling.

Client UI installation, skill auto-selection in a live conversation, model narrative quality, and cloud tunnel connectivity require testing in the target application/account. They are not claimed by the automated tests. No hosted endpoint has been deployed.

Run `npm run typecheck`, `npm test`, `npm run test:journal`, and `npm run package:plugin`. Skill frontmatter can also be validated with the skill-creator validator when available in the development environment.

## Rules referee (0.5.0)

The scripted workflow tests cover pre-roll requirements, exact step specifications, reported-roll bounds, duplicate recovery, required/optional dice, explicit amendments, exact approved atomic effects, direct-write guards (including replacement/map/correction paths), administrative fallback and invariant failures, stale re-review with preserved dice, pure narrative checkpoints, policy activation, legacy compatibility, private player filtering, and restart/export/import. An illustrative Briar Ford potion workflow resolves actual dice, consumes the potion, heals the character and records bonus-action use together. These tests validate protocol/state behavior, not a complete D&D engine.

A bounded host subagent, with no model override, independently read the rules-referee skill and pinned references for seven isolated cases. It rejected impossible jumping and unavailable slots/actions, preserved dangerous legal intent while asking for missing combat facts, rejected success after a saved failed roll, requested missing feature text, and checked the potion house rule. It identified a genuine 2014/2024 potion action-cost difference. The test deliberately supplied incomplete fixtures, so clarification verdicts are expected rather than fabricated statistics. It made no campaign mutations or external calls. Actual host delegation was exercised; an entire interactive live campaign with automatically selected skills was not.

That evaluation exposed poor rule-search ranking. Search now favors exact phrases and headings with term-frequency weighting; regression checks locate the jump glossary and potion equipment entry. Text extraction retains multi-column/table limitations; callers can inspect original PDF references when necessary. Source edition/page validation and checksums cannot verify that a citation logically supports a ruling.

One pending action is supported at a time. The server trusts supplied referee responses and fictional context; actor/model strings are not independent-authorship authentication. Complete action budgets, class features, collision/line-of-sight and spell resolution remain adjudicated rather than automatically enforced. The explicit administrative fallback is covered by tests, not by intentionally disabling a user's host capability.

## Experimental local Ollama adapter (2026-10-22)

The local adapter was exercised with Codex CLI 0.162.1, Ollama 0.40.8 and `qwen3.5:9b` Q4_K_M on an NVIDIA RTX 5060 Ti with 16 GiB VRAM and about 60 GiB system RAM. Ollama reported a 65,536-token runner entirely on GPU, using approximately 7.7 GB for the model allocation; desktop and other GPU allocations add to that figure. This is one measured configuration, not a fit guarantee for other models, contexts or hardware.

All 108 automated tests, typecheck, isolated real journal integration, Electron UI smoke, LAN browser smoke, formatting and plugin packaging passed. Local-specific tests cover metadata capability/context checks, arbitrary model selection, hardware suggestions, isolated model/session identity, actual runner allocation checks, memory-tool prerequisites, continuity notes after effects, exact retries, image content compatibility, oversized submissions, native compaction completion and correlated continuation steering. Eight consecutive local campaign-tool failures stop the turn without replay; successful calls reset that budget. The existing plugin and hosted-provider tests remain in the suite; live authenticated Codex/Antigravity scenarios were not rerun for this increment.

Live Qwen probes demonstrated a campaign-tool connection, exact recall of a saved boat agreement and password, and successful damage/publication in some runs. A separate controlled image probe identified a solid red image correctly after fixing two transport issues: unknown models need image modalities in the Codex catalog, and Codex can discard MCP image blocks when it prefers a separate structuredContent result. Local image responses now retain JSON as text alongside the PNG; default plugin responses remain unchanged.

The 32k-context full-scenario stress runs did not pass reliably. A subsequent 64k run also repeated malformed mutation calls and was stopped after about 148 seconds; it did not pass. Observed failures included malformed mutation arguments, omitted requested effects and repeated compaction. Native automatic compaction occurred, and the tests exposed a continuation that returned to an old connection check; the adapter now steers the same active turn with only the current request. These fixes have protocol coverage, but a compaction event alone does not demonstrate successful gameplay continuation. Journal guards enforce retrieval and saving steps, not the semantic correctness of the model's notes or narration.

A separate `dm-qwen3.5:9b` configuration (`FROM qwen3.5:9b`, `num_ctx 65536`, `temperature 0.2`) passed the complete 64k synthetic scenario in about 252 seconds with outbound network unavailable. The run checked saved boat/password recall, exactly two damage, duplicate submission without new effects, magenta map-image interpretation, explicit native compaction, process restart and resumed password/HP recall, with the private sentinel absent from public snapshots. Its four player turns took approximately 94, 30, 28 and 34 seconds. No automatic compaction occurred at 64k in this short successful run; automatic compaction was observed only in the separate failing 32k stress runs. A single successful run does not prove the sampling change caused the improvement or establish sustained reliability.

The live test in `test/integration/local.mjs` is opt-in and defaults to 64k. Setting `DM_LOCAL_CONTEXT=32768 DM_REQUIRE_AUTO_COMPACT=1` additionally requires automatic compaction. Trials also ran in a private Linux network namespace containing only loopback, with a separately owned Ollama server and isolated journal daemon. Those trials used deliberate keyword fallback and do not establish offline semantic embedding quality. No existing shared daemon was stopped or reconfigured. Local artwork generation, independent referee quality, and sustained campaign reliability remain unverified or unsupported as described in [desktop.md](desktop.md).
