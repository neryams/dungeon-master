# Installation and campaign setup

## Generated campaign plugin (preferred)

Run `npm ci` and `npm run build` in the source repository, then:

```bash
node dist/cli.js init briar-ford --name "Briar Ford" --edition 2024
```

The command initializes a new campaign folder under `~/Campaigns`, initializes local Git, copies the four skills into `.dm/plugin`, and writes a portable plugin manifest with an explicit stdio command bound to that campaign. `.agents/plugins/marketplace.json` points at that generated plugin. `.codex/config.toml` enables its unique project marketplace entry.

Open the campaign folder as a trusted local project. Restart the client if its plugin directory is stale; select the campaign's marketplace, install Dungeon Master, and open a new conversation. Ask: “Use Dungeon Master to create my party and opening scene.” A fresh initialized campaign has no game events yet.

The generated configuration points to this installation's built server. Keep that installation in place. After moving it or updating skills, preserve/merge existing project configuration and regenerate setup with `dungeon-master setup --campaign ...`. Setup refuses to overwrite existing config or marketplace files. Remove only previously generated files after reviewing them, or merge the values manually. Runtime data under `.dm` is rebuildable, except that it also holds the generated plugin copy; setup regenerates that copy.

## Direct connection fallback

Clients without local plugin marketplace support can connect the same domain MCP server directly:

```toml
[mcp_servers.dungeon-master]
command = "/absolute/path/to/node"
args = ["/absolute/path/to/dungeon-master/dist/server.js", "--campaign", "/absolute/path/to/campaign"]
```

Merge this into the campaign's `.codex/config.toml`. Do not enable both the generated plugin's server and this direct connection. Copy the four skill folders from this repository's `skills/` into the campaign's `.agents/skills/` for local skill discovery. Start a new conversation and verify that `campaign_status` returns the intended campaign name.

For another MCP client, use its equivalent stdio settings. Only the DM server is registered; its journal MCP connection remains internal.

## Portable plugin package

`npm run package:plugin` creates a portable folder and archive. Extract it, install dependencies with `npm ci`, build, and run `npm link` if using its generic `mcp.json`, whose command is `dungeon-master-mcp`. The command reads `--campaign`, then `DM_CAMPAIGN_ROOT`, then searches upward from cwd for `campaign.json`. Never rely on cwd when the client cannot guarantee it. The explicit generated campaign plugin is preferred for multiple campaigns.

The source repository's development marketplace points at `build/plugin`, generated by the packaging command. That generic development entry is not bound to a campaign; configure the process environment before using it.

Official manifest and marketplace reference: https://developers.openai.com/plugins/build/plugins

## Dependency override and failures

Set `DM_JOURNAL_SERVER` in the server process environment to use a particular built journal checkout. The adapter passes `JOURNAL_RAG_WORKSPACE` explicitly and runs the proxy in the campaign folder. Preserve `sources: ["journal"]` and `cachePath: ".journal-rag/index.json"`; those locations are checked to prevent accidental use of another corpus.

Node and Git are prerequisites. The optional journal dependency may be omitted by npm if installation fails. Fix that installation or use the override, then run `journal-sync`. Do not repeat already committed game actions.

If a derived journal file is damaged, preserve it outside `journal/`, confirm its authoritative record in the event history, remove only the damaged derived file, and run `journal-sync`. Its original record will be re-created from the event. Neither deleting index caches nor repairing derived Markdown should change authoritative event files.
